# Code QnA 요약

## 1. 한 줄 정의

Slack에서 코드 관련 질문을 던지면 AI 에이전트가 사내 GitLab 저장소를 직접 탐색하고, 근거 파일과 함께 답변을 돌려주는 사내 코드 질문 봇

## 2. 사용 시나리오

| 질문 유형             | 처리 방식                                                                    |
| --------------------- | ---------------------------------------------------------------------------- |
| 단일 화면 질문        | 화면을 식별하고 단일 저장소를 분석한다.                                      |
| 프론트/서버 양쪽 질문 | 비교나 호출 관계 의도로 판단되면 화면 그래프를 따라 관련 저장소를 함께 본다. |
| 스레드 후속 질문      | 이전 답변과 스레드 맥락을 반영해 화면 매핑을 다시 해석한다.                  |
| 모호한 질문           | 질문 정제, 후보 화면 축소, AI 최종 판단을 거쳐 분석 대상을 좁힌다.           |
| 코드와 무관한 질문    | 분석 가능성 판정에서 걸러 가벼운 안내만 응답한다.                            |

## 3. 전체 요청 플로우

```text
Slack 멘션 수신
  - 진행 상태 메시지 생성
  ↓
요청 ID 발급 + 스레드 맥락 조회
  ↓
등록된 화면 목록 로드
  ↓
질문 정제 + 화면/의도/키워드 추출
  ↓
분석 가능성 판단
  ├─ 분석 불가: 안내 응답
  └─ 분석 가능: 저장소 매핑으로 진행
  ↓
저장소와 브랜치 확정
  ↓
필요 시 관련 프론트/서버 저장소 묶음
  ↓
LangGraph 에이전트 실행
  ├─ 탐색 단계
  └─ 검증 단계
  ↓
답변 구조 검증
  ├─ 성공: 구조화된 Slack 답변
  └─ 실패: 마크다운 폴백 답변
  ↓
Slack 응답 + DB 적재
```

본체 서버는 Bedrock LLM으로 질문 정제/화면 판단/에이전트 추론/답변 구조화를 수행하고, 사내 Workflow API로 GitLab 저장소를 탐색한다. 운영 DB에는 요청 기록, 화면 등록 정보, 비용, 성공 여부, 피드백이 쌓인다.

## 4. 화면을 정하는 방식

결정적 규칙만으로 화면을 확정하지 않고, 규칙은 후보를 좁히는 데 사용하며 최종 판단은 LLM이 수행한다.

| 단계          | 역할                                                                           |
| ------------- | ------------------------------------------------------------------------------ |
| 질문 정제     | 오타/구어체를 정리하고 스레드 맥락, 핵심 명사구를 반영한다.                    |
| 후보 축소     | 정확 일치, 오타 허용 유사 일치, 키워드 매칭, 토큰 겹침으로 상위 후보만 남긴다. |
| LLM 최종 판단 | 화면, 질문 의도, 저장소 종류, 분석 가능성, 핵심 키워드를 결정한다.             |

화면명은 대소문자, 공백, 구분기호를 정규화한다. 운영자가 등록한 별칭, 대표 질문 예시, 자매 저장소 구분 힌트도 함께 사용해 "주문내역", "주문 내역", "OrderHistory"처럼 같은 대상을 여러 방식으로 부르는 문제를 흡수한다.

## 5. 저장소 매핑과 관련 저장소 탐색

화면 등록 정보에는 화면 이름, 저장소 URL, 화면 종류, GitLab 숫자 ID, 별칭, 대표 질문, 구분 힌트, 담당자, 사전 분석 결과가 저장된다.

프론트와 서버처럼 화면 사이의 호출 관계가 등록되어 있으면, 질문 의도가 비교나 호출 관계 추적인 경우 관련 저장소를 함께 묶어 분석한다.

## 6. 에이전트 실행 구조

에이전트는 탐색과 검증 두 단계로 동작한다.

| 단계           | 역할                                            | 한도      |
| -------------- | ----------------------------------------------- | --------- |
| 탐색           | GitLab 도구로 코드를 찾고 초안 답변을 만든다.   | 최대 25회 |
| 검증 준비      | 탐색 초안을 확정하고 남은 도구 호출을 폐기한다. | -         |
| 검증           | 초안을 다시 보고 부족한 근거만 보완한다.        | 최대 5회  |
| 답변 구조 검증 | 정해진 답변 형식으로 정리한다.                  | -         |

반복 한도에 도달해도 예외로 끝내지 않고, 탐색은 답변을 강제로 마무리하고 검증은 초안을 최종 답변으로 사용한다.

## 7. GitLab 탐색 도구

도구는 처음부터 파일 본문을 크게 읽기보다, 저장소 후보 식별 → 구조 파악 → 코드 위치 찾기 → 근거 파일 읽기 순서로 점진적으로 좁혀 간다.

| 도구                     | 역할                                                      |
| ------------------------ | --------------------------------------------------------- |
| 화면 매핑 조회           | 화면이 어느 저장소/브랜치에 연결되는지 확인한다.          |
| 저장소 트리              | 저장소의 폴더 구조를 파악한다.                            |
| 파일 구조 요약           | 본문 전체 대신 함수, 클래스, import 같은 구조만 확인한다. |
| 코드 검색/배치 검색      | 단일 또는 여러 키워드로 저장소 전체를 검색한다.           |
| 파일 안 라인 검색        | 큰 파일 전체 대신 키워드 주변 맥락만 가져온다.            |
| 파일 본문 단일/배치 조회 | 최종 근거 라인을 확인한다.                                |

배치 조회, 라인 검색, 파일 구조 요약은 에이전트가 한 턴에 더 많은 근거를 확인하게 해서, iteraction 수와 token 사용량을 줄이는 걸 목표로 한다

## 8. 답변 구조

최종 답변은 LLM이 자유 마크다운으로만 생성하지 않고, 정해진 구조로 파싱한다.

- 요약: 질문에 대한 결론 한 줄
- 본문: Slack에 표시할 상세 설명
- 근거 파일 목록: 어떤 파일과 라인을 보고 답했는지
- 담당자 멘션 후보: 화면 등록 정보에 있는 담당자
- 증거 항목: 모니터링과 운영 콘솔에서 활용할 근거 데이터

구조화(JSON)에 성공하면 Slack, Admin, 모니터링 화면이 같은 데이터를 각자 방식으로 렌더링한다. 구조 검증에 실패하면 마크다운 원문으로 폴백해 사용자에게 답변이 끊기지 않게 한다.

답변에 인용된 파일이 실제 요청 중 읽힌 파일인지도 대조한다. 읽지 않은 파일이 답변에 등장하면 운영자가 볼 수 있도록 환각 경고를 남긴다.

## 9. 사용자와 운영자를 위한 기능

- 진행 상태 표시: 답변 생성 중에도 Slack 메시지를 갱신해 현재 단계를 보여 준다.
- 스레드 후속 질문 지원: 같은 스레드의 이전 질문과 답변을 반영해 후속 질문을 해석한다.
- 사용자 노출 번호: 답변 푸터에 `#7` 같은 짧은 번호를 붙여 요청을 쉽게 지칭할 수 있게 한다.
- 담당자 후보 노출: 화면 등록 정보의 담당자를 답변에 함께 보여 준다.
- 비용 표시: 캐시 적용 전후 비용을 함께 계산해 운영 콘솔에서 확인할 수 있다.
- 실패 분류: 화면 인식 실패, 저장소 미등록, 에이전트 내부 실패 등으로 실패 사유를 나눠 사용자 안내와 운영 통계에 활용한다.
