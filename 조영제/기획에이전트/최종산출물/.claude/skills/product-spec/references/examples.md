# 한국어 기획서 예시 (Korean Spec Examples)

SKILL.md의 전 단계에서 톤, 깊이, 포맷의 기준으로 참조됩니다.
좋은 예와 나쁜 예를 비교하여 품질 기준을 제시합니다.

---

## PRD 예시 — "간편 결제 도입"

### 1. 개요 (Overview) — 좋은 예

```markdown
# 간편 결제 도입 PRD

| 항목 | 내용 |
|------|------|
| 작성자 | 김PM |
| 작성일 | 2026-04-25 |
| 버전 | v0.1 (초안) |
| 상태 | 검토중 |
| 리뷰어 | 개발팀 리드, 디자인팀 리드 |

**한 줄 요약**: 기존 3단계 결제 프로세스를 1단계로 축소하여 결제 완료율을 55%에서 75%로 개선한다.
```

❌ **나쁜 예**: "결제 시스템을 개선합니다." — 구체성 없음, 측정 불가

---

### 3. 배경 및 문제 정의 — 좋은 예

```markdown
## 배경 및 문제 정의 (Background & Problem Definition)

### 현재 상황 (As-Is)
현재 결제 프로세스는 3단계로 구성:
1. 배송지 입력 → 2. 결제 수단 선택 → 3. 최종 확인

### 문제점
- 결제 페이지 이탈률: **45%** (업계 평균 25% 대비 20%p 높음)
- 2단계(결제 수단 선택)에서 전체 이탈의 **62%** 발생
- 모바일 사용자의 이탈률이 데스크톱 대비 **1.8배** 높음
- 월 추정 매출 손실: **약 2.3억원** (이탈 사용자 × 평균 주문금액 기준)

### 해결 시급성
Q2 매출 목표 달성을 위해 결제 전환율 개선이 최우선 과제로 선정됨.
경쟁사 A는 이미 원클릭 결제 도입 후 전환율 30% 개선을 공개 발표.
```

❌ **나쁜 예**:
```markdown
## 배경
결제가 불편하다는 CS가 많아서 개선이 필요합니다.
```
— 데이터 없음, "많다"의 기준 불명확, 영향도 미산정

### 4. 목표 및 성공 지표 — 좋은 예

```markdown
## 목표 및 성공 지표 (Goals & Success Metrics)

### 비즈니스 목표
간편 결제 도입으로 결제 전환율을 개선하여 Q2 매출 목표를 달성한다.

### 성공 지표

| 지표 | 현재값 | 목표값 | 측정 기간 | 측정 방법 |
|------|--------|--------|----------|----------|
| 결제 완료율 | 55% | 75% | 출시 후 4주 | GA 퍼널 |
| 결제 소요 시간 | 평균 47초 | 15초 이하 | 출시 후 2주 | 클라이언트 로그 |
| 결제 관련 CS | 월 320건 | 월 100건 이하 | 출시 후 4주 | CS 시스템 |

### 비목표 (Non-goals)
- 해외 결제 지원 → Q3 로드맵에 별도 배정
- 정기구독 결제 → 별도 프로젝트로 진행 예정
- 포인트/쿠폰 결제 통합 → 이번 범위에서 제외, Phase 2에서 검토
```

### 6. 요구사항 — 좋은 예

```markdown
## 요구사항 (Requirements)

### 기능 요구사항

| ID | 설명 | 우선순위 | 인수 조건 |
|----|------|---------|----------|
| FR-001 | 최근 사용 결제 수단 자동 선택 | P0 | 마지막 결제 수단이 기본 선택되어 있어야 함 |
| FR-002 | 배송지 최근 주소 자동 입력 | P0 | 최근 3개 주소 중 선택 가능, 마지막 사용 주소가 기본값 |
| FR-003 | 원클릭 결제 버튼 | P0 | 기본 결제수단+기본 배송지 선택 시 1번 탭으로 결제 완료 |
| FR-004 | 결제 진행 상태 표시 | P1 | 결제 처리 중 로딩 상태, 예상 소요 시간 표시 |
| FR-005 | 결제 실패 시 자동 재시도 | P2 | 네트워크 에러 시 최대 2회 자동 재시도, 실패 시 수동 재시도 안내 |

### 비기능 요구사항

| 항목 | 요구사항 |
|------|---------|
| 성능 | 결제 API 응답 p95 < 500ms |
| 보안 | PCI-DSS 준수, 카드 정보 토큰화 저장 |
| 가용성 | 결제 서비스 SLA 99.95% |
| 접근성 | WCAG 2.1 AA 기준 충족 |
```

### 7. 사용자 시나리오 — 좋은 예

```markdown
## 사용자 시나리오 (User Scenarios)

### 시나리오 1: 재구매 사용자 — 원클릭 결제 (Happy Path)

**Given** 이전에 결제 이력이 있는 로그인 사용자가
**When** 상품 상세에서 "바로 구매"를 탭하면
**Then** 마지막 결제수단 + 마지막 배송지가 자동 선택된 결제 확인 화면이 표시되고,
"결제하기" 버튼 1번 탭으로 결제가 완료된다.

### 시나리오 2: 저장된 결제수단이 만료됨 (Edge Case)

**Given** 저장된 카드의 유효기간이 만료된 사용자가
**When** 원클릭 결제를 시도하면
**Then** "저장된 카드가 만료되었습니다" 메시지와 함께 결제수단 변경 화면으로 이동하고,
새 카드 등록 또는 다른 결제수단 선택을 안내한다.

### 시나리오 3: 결제 중 네트워크 오류 (Error)

**Given** 결제 처리 중인 사용자의 네트워크가 끊어지면
**When** 결제 API 호출이 타임아웃되면
**Then** 자동으로 최대 2회 재시도하고, 재시도 실패 시
"결제가 완료되지 않았습니다. 다시 시도해주세요" 메시지를 표시하며,
중복 결제가 발생하지 않도록 멱등성 키로 보호한다.
```

## 유저 스토리 예시

### 좋은 유저 스토리

```markdown
### US-001: 원클릭 결제

**에픽**: 간편 결제 도입

**스토리**:
결제를 진행 중인 재구매 고객으로서,
저장된 결제수단과 배송지로 한 번에 결제하고 싶다.
매번 정보를 입력하는 것이 번거롭기 때문이다.

**인수 조건**:
- Given: 이전 결제 이력이 있는 로그인 사용자
- When: "바로 구매" 버튼 탭
- Then: 1탭으로 결제 완료 (결제수단/배송지 자동 선택)

**INVEST 체크**:
- [x] Independent: 다른 스토리 없이 단독 개발 가능
- [x] Negotiable: 자동 선택 로직은 협의 가능
- [x] Valuable: 결제 전환율 직접 개선
- [x] Estimable: 3 스토리 포인트
- [x] Small: 1 스프린트 내 완료 가능
- [x] Testable: Given/When/Then 명확
```

### 나쁜 유저 스토리

```markdown
❌ "사용자로서, 결제를 쉽게 하고 싶다."
```
— 페르소나 불명확, 행동 모호, 가치 미기술, 인수 조건 없음

## 톤 & 스타일 가이드

### 지향
- 데이터로 말한다: "많다" 대신 "320건/월"
- 구체적으로 쓴다: "개선한다" 대신 "55% → 75%로 개선한다"
- 개발팀이 바로 구현할 수 있는 수준의 상세도
- 각 요구사항에 "왜"가 담겨 있어야 한다

### 지양
- 형용사로 뭉개기: "빠르게", "편리하게", "직관적으로"
- 범위 없는 목표: "사용자 경험 개선"
- 근거 없는 우선순위: 왜 P0인지 설명 없이 P0 부여
- 다이어그램과 텍스트의 내용 중복
