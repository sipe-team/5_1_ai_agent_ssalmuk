# 품질 검증 게이트 (Quality Gates)

SKILL.md의 Step 7에서 참조됩니다.
기획서 출력 전 반드시 이 검증을 통과해야 합니다.

## 기획서 타입별 체크리스트

### PRD 체크리스트
- [ ] 문제 정의가 구체적인 데이터나 사례로 뒷받침되는가?
- [ ] 성공 지표가 측정 가능한가? (현재값 → 목표값 포함)
- [ ] 비목표(Non-goals)가 명시적으로 기술되었는가?
- [ ] 모든 기능 요구사항에 우선순위(P0/P1/P2)가 부여되었는가?
- [ ] 각 기능 요구사항에 인수 조건(Acceptance Criteria)이 있는가?
- [ ] 사용자 시나리오가 Happy Path + Edge Case + Error를 포함하는가?
- [ ] 기술 제약사항이 개발팀이 이해할 수 있게 기술되었는가?
- [ ] 리스크마다 완화 방안이 있는가?
- [ ] 범위 외 항목이 최소 3개 이상 명시되었는가?
- [ ] 다이어그램이 텍스트 설명을 보완하는가? (중복이 아닌 보완)
- [ ] 모든 클릭 가능 요소에 클릭 명세(동작 + 네비게이션 타입)가 있는가?
- [ ] 모든 화면/컴포넌트에 4가지 상태(로딩/성공/빈값/에러)가 정의되었는가?
- [ ] 페이지 전환 흐름(push/replace/pop/modal)이 명시되었는가?
- [ ] 폼/입력 필드에 유효성 검증 규칙과 에러 메시지가 있는가?
- [ ] In/Out/Future 스코프 테이블이 요구사항과 1:1 매칭되는가?
- [ ] 외부 API가 있으면 API 명세(엔드포인트, 에러 코드, 인증 방식)가 포함되었는가?
- [ ] 보안 기준선(인증 방식, PII 여부, 감사 로그)이 식별되었는가?
- [ ] 비기능 요구사항에 수치 기준이 최소 2개 이상 명시되었는가? (예: p95 응답시간, 에러율)
- [ ] 이해관계자 RACI가 작성되었는가?
- [ ] 사이드이펙트 영향 테이블이 작성되고, 영향 받는 기능별 회귀 테스트 필요 여부가 명시되었는가?
- [ ] 크로스팀 의존성이 식별되고 담당자/일정이 명시되었는가?
- [ ] 마일스톤이 최소 3개 이상이고 크리티컬 패스가 식별되었는가?
- [ ] 상태 관리 힌트(8-5)에 주요 데이터의 서버/글로벌/로컬 분류가 있는가?
- [ ] 디자인 핸드오프(8-6)에 반응형 브레이크포인트가 정의되었는가?
- [ ] 각 핵심 섹션(인터랙션 명세, API 명세, 시나리오)이 독립적으로 읽혀도 이해 가능한가? (cold-start 독립성)
- [ ] 변경 로그가 존재하고, 모든 수정에 사유가 기록되었는가?

### Feature Spec 체크리스트
- [ ] 기능의 목적과 배경이 PRD/상위 문서와 연결되어 있는가?
- [ ] 상세 기능 흐름이 단계별로 기술되었는가?
- [ ] 클릭 명세 테이블이 화면별로 작성되었는가?
- [ ] UI 상태 명세(로딩/성공/빈값/에러)가 컴포넌트별로 있는가?
- [ ] 페이지 전환 흐름(push/replace/pop/modal)이 명시되었는가?
- [ ] 입력/출력 데이터와 유효성 검증 규칙이 명시되었는가?
- [ ] 상태 전이(State Transition)가 정의되었는가?
- [ ] 에러 처리 및 예외 상황별 대응이 기술되었는가?
- [ ] 다른 기능과의 의존성/영향 범위가 파악되었는가?
- [ ] 권한 및 접근 제어 요구사항이 명시되었는가?
- [ ] 다국어/접근성 요구사항이 고려되었는가?
- [ ] QA 테스트 시나리오가 포함되었는가?
- [ ] 사이드이펙트 영향 테이블이 작성되었는가?
- [ ] 경계값 테스트 테이블(필드, 최솟값, 최댓값, 기대 동작)이 있는가?
- [ ] 동시성 시나리오가 최소 1개 이상 포함되었는가?

### User Story 체크리스트
- [ ] **Independent**: 다른 스토리와 독립적으로 개발/배포 가능한가?
- [ ] **Negotiable**: 구현 방식이 아닌 가치 중심으로 기술되었는가?
- [ ] **Valuable**: 사용자 또는 비즈니스에 명확한 가치를 제공하는가?
- [ ] **Estimable**: 개발팀이 공수를 추정할 수 있을 만큼 구체적인가?
- [ ] **Small**: 한 스프린트 내에 완료 가능한 크기인가?
- [ ] **Testable**: 완료 여부를 객관적으로 검증할 수 있는가?
- [ ] 페르소나가 구체적인 역할로 정의되었는가? ("사용자"가 아닌 구체적 역할)
- [ ] 인수 조건이 Given/When/Then 형식으로 작성되었는가?
- [ ] 스토리 포인트 또는 T-shirt 사이즈가 추정되었는가?
- [ ] 의존성이 있다면 명시되었는가?

### Tech Spec 체크리스트
- [ ] 시스템 아키텍처 다이어그램이 포함되었는가?
- [ ] API 엔드포인트가 Request/Response 스키마와 함께 정의되었는가?
- [ ] 데이터 모델/스키마 변경사항이 명시되었는가?
- [ ] 성능 요구사항이 수치로 정의되었는가? (TPS, 응답시간, 동시접속 등)
- [ ] 보안 요구사항이 OWASP 기준 등으로 검토되었는가?
- [ ] 인증/인가 방식이 구체적으로 기술되었는가?
- [ ] 확장성(Scalability) 전략이 명시되었는가?
- [ ] 장애 대응(Failover/Fallback) 방안이 있는가?
- [ ] 모니터링/알림 기준이 정의되었는가?
- [ ] 마이그레이션 계획이 포함되었는가? (해당 시)
- [ ] 롤백 전략이 명시되었는가?

## 안티패턴 (Anti-Patterns)

### 문제 정의 안티패턴
❌ 나쁜 예: "사용자 경험을 개선한다"
✅ 좋은 예: "결제 페이지 이탈률이 45%로, 업계 평균(25%) 대비 20%p 높다. 주요 원인은 3단계 결제 프로세스의 복잡성이다."

### 성공 지표 안티패턴
❌ 나쁜 예: "사용자 만족도를 높인다"
✅ 좋은 예: "결제 완료율: 55% → 75% (출시 후 4주 내) | 측정: GA 퍼널 분석"

### 요구사항 안티패턴
❌ 나쁜 예: "빠르게 로딩되어야 한다"
✅ 좋은 예: "메인 피드 API 응답시간 p95 < 200ms (현재 p95: 850ms)"

### 유저 스토리 안티패턴
❌ 나쁜 예: "사용자로서, 좋은 경험을 원한다"
✅ 좋은 예: "결제를 진행 중인 구매자로서, 배송지를 최근 주소에서 선택하고 싶다. 매번 입력하는 것이 번거롭기 때문이다."

### 범위 안티패턴
❌ 나쁜 예: 범위 외 항목이 없음
✅ 좋은 예: "범위 외: 해외 결제 지원, 정기구독 결제, 포인트 결제. 이유: 해외 PG 연동은 Q3 로드맵에 별도 배정."

### 다이어그램 안티패턴
❌ 나쁜 예: 텍스트와 동일한 내용을 다이어그램으로 반복
✅ 좋은 예: 텍스트는 "왜"를 설명하고, 다이어그램은 "어떻게"의 구조를 시각화

### 인수 조건 안티패턴
❌ 나쁜 예: "정상적으로 동작해야 한다"
✅ 좋은 예: "Given: 장바구니에 3개 상품이 있을 때 / When: 전체 선택 해제 후 1개만 재선택 / Then: 선택된 1개 상품의 금액만 결제 금액에 반영된다"

### 인수 조건 Then절 안티패턴
❌ 나쁜 예: "Then 결제가 완료된다"
✅ 좋은 예: "Then POST /v1/payments 응답 status가 'completed'이고, 결제 완료 화면에 ORD-{숫자} 형식의 주문번호가 표시된다"

Then절은 반드시 다음 중 하나를 명시:
1. **UI 변화**: 화면에 보이는 구체적 상태/텍스트
2. **API 응답**: 응답 필드와 기대값
3. **데이터 변화**: DB/이벤트 상태 변경

### 리스크 안티패턴
❌ 나쁜 예: "일정이 지연될 수 있다"
✅ 좋은 예: "리스크: PG사 API 연동 지연 (확률: 중, 영향: 상) / 완화: 샌드박스 환경 사전 확보, 대체 PG사 후보 선정 완료"

## 테스트 자동화 가이드 (Test Automation Guide)

기획서의 시나리오/인수 조건을 테스트로 전환할 때의 기준입니다.

| 시나리오 유형 | 테스트 레벨 | 자동화 우선순위 |
|------------|-----------|-------------|
| Happy Path (핵심 시나리오) | E2E | P0 — 반드시 자동화 |
| 에러 시나리오 (API 실패, 네트워크 오류) | 통합 테스트 | P1 |
| 폼 유효성 검증 | 단위 테스트 | P0 — 반드시 자동화 |
| 경계값 테스트 | 단위 테스트 | P1 |
| 동시성 시나리오 | 부하 테스트 | P2 |
| UI 상태 (로딩/빈값/에러) | 컴포넌트 테스트 | P1 |

테스트 ID 태깅: 각 인수 조건에 `TC-{기능}-{번호}` ID를 부여하여 추적 가능하게 합니다.

### 점수 계산
`완성도 = Σ(섹션_가중치 × 섹션_완성도) / 100`

각 섹션의 완성도는 0~100%:
- **100%**: 모든 항목 충족, 구체적 데이터 포함
- **75%**: 대부분 충족, 일부 항목 구체성 부족
- **50%**: 기본 구조만 있고 상세 내용 부족
- **25%**: 존재하지만 형식적
- **0%**: 누락

### 통과 기준
- **80% 이상**: 통과 — 기획서 출력
- **60~79%**: 경고 — 부족한 섹션을 명시하고 사용자에게 보완 여부 확인
- **60% 미만**: 차단 — 부족한 섹션을 나열하고 디스커버리 인터뷰로 복귀
