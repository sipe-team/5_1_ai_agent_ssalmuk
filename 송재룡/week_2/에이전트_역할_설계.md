# Week 2: 에이전트 역할 설계

## 에이전트 구성

Week 1에서 정의한 장전 리서치 자동화 문제를 해결하기 위해, 아래 에이전트와 helper 계층을 설계한다. 현재 구현은 LLM 없이 deterministic rule-based 방식으로 동작하며, 이후 `llm_client`를 주입할 수 있도록 인터페이스를 열어둔다.

### 1. MarketDataAgent

- **역할**: 시장 snapshot을 해석해 risk tone과 시장 근거를 생성
- **입력**: `MarketSnapshot` list
- **출력**: `MarketDataAnalysis`
- **주요 판단**: KOSPI/KOSDAQ 등락률, collection failure, mock/live 상태
- **출력 예시**: `risk_off`, `KOSPI -1.38%, KOSDAQ -2.29%`, 장중 확인 포인트

### 2. NewsContextAgent

- **역할**: 정제된 뉴스에서 시장 변수와 중요 뉴스 근거를 추출
- **입력**: `CleanNewsItem` list
- **출력**: `NewsContextAnalysis`
- **주요 판단**: category 기반 key variables, high importance news, data gaps
- **출력 예시**: `fx_risk`, `rate_policy_risk`, `geopolitical_risk`, `market_flow`

### 3. MarketNewsSynthesisAgent

- **역할**: 시장 흐름과 뉴스 변수를 결합해 장전 핵심 판단 생성
- **입력**: `MarketDataAnalysis`, `NewsContextAnalysis`
- **출력**: `MarketNewsSynthesis`
- **주요 판단**: overall risk tone, market-news connection, intraday watch points
- **주의점**: 단정적 방향 예측 대신 관찰 변수와 시나리오 중심으로 표현

### 4. CandidateTaggingAgent

- **역할**: static profile과 오늘 시장 변수를 결합해 dynamic context tag 생성
- **입력**: `Candidate`, `MarketNewsSynthesis`
- **출력**: `CandidateTaggingResult`
- **구성**:
  - `CandidateStaticProfile`: 변하지 않는 기본 성격
  - `CandidateDynamicContext`: 오늘 시장 변수와 연결된 tag/evidence/reason
- **예시 rule**:
  - `fx_risk` + `fx_sensitive` → `환율 민감도 확인`
  - `rate_policy_risk` + `rate_sensitive` → `성장주 밸류에이션 부담 확인`
  - `geopolitical_risk` + `oil_cost` → `원가/유가 리스크 확인`
  - `market_flow` + `market_beta` → `지수 방향성 확인`

### 5. CandidateContextAgent

- **역할**: 후보별 오늘의 관찰 이유, 연결 변수, 확인 포인트, 리스크 생성
- **입력**: scored candidates, `MarketNewsSynthesis`
- **출력**: `CandidateExplanation` list
- **주요 기능**:
  - static profile summary와 today observation reason 분리
  - dynamic tag 기반 설명 생성
  - unknown ticker 과대 설명 방지
  - 유사 profile 후보 중복 note 부여

### 6. RiskReviewAgent

- **역할**: 리포트 문구에서 투자 권유로 오해될 표현을 완화
- **입력**: synthesis, candidate explanations
- **출력**: `ReviewedPremarketNarrative`
- **검사 표현**: 추천, 매수, 상승 확정, 보장 등
- **출력 원칙**: 참고용 관찰 정보, 시나리오, 리스크, 확인 필요

### 7. ReportEditorAgent

- **역할**: reviewed narrative를 Telegram-friendly compact content로 편집
- **입력**: reviewed narrative, generated_at, section status
- **출력**: `CompactReportContent`
- **주의점**: formatter 내부에 tag 판단 로직을 넣지 않고, 이미 생성된 explanation을 사용자용 포맷으로 정리

## 에이전트 간 관계

```
[MarketDataClient] ──▶ [MarketDataAgent]
                                      │
[NewsClient] ─▶ [News Cleaning] ─▶ [NewsContextAgent]
                                      │
                                      ▼
                         [MarketNewsSynthesisAgent]
                                      │
[Candidate Universe] ─▶ [Scoring] ─▶ [CandidateTaggingAgent]
                                      │
                                      ▼
                           [CandidateContextAgent]
                                      │
                                      ▼
                              [RiskReviewAgent]
                                      │
                                      ▼
                             [ReportEditorAgent]
                                      │
                                      ▼
                              [TelegramClient]
```

## 책임 분리 원칙

- Provider client는 데이터 수집과 최소 정규화만 담당한다.
- Formatter는 이미 만들어진 content를 문자열로 배치하는 역할만 담당한다.
- 후보 tag 판단은 Agent 계층에서 수행한다.
- static profile은 fallback anchor이며 오늘의 관찰 이유를 직접 만들지 않는다.
- dynamic context는 market variables와 static sensitivity의 연결성에 기반한다.
- LLM은 아직 도입하지 않고, rule-based deterministic agent로 테스트 가능성을 우선한다.
