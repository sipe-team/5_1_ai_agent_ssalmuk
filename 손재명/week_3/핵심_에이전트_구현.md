# Week 3: 핵심 에이전트 구현 및 기본 동작 검증

## 목표

Week 2에서 설계한 6개 에이전트 중 **장애 분류 에이전트**와 **유사 장애 검색 에이전트**를 우선 구현하고, 기본 동작을 검증한다.

## 구현 대상 선정 이유

| 에이전트 | 선정 이유 |
| --- | --- |
| 장애 분류 에이전트 (Classifier) | 전체 워크플로우의 시작점이며, 다른 에이전트의 입력을 생성하는 핵심 역할 |
| 유사 장애 검색 에이전트 (RAG) | RAG 파이프라인 검증이 프로젝트 전체의 기술적 핵심이며, 실무 효과가 가장 큼 |

## 1. 장애 분류 에이전트 구현

### 기능 정의

- 장애 접수 내용(제목, 설명, 에러 로그)을 입력받아 카테고리와 심각도를 자동 판단
- JSON 형식으로 구조화된 결과 출력

### 입출력 스펙

**입력**:
```json
{
  "title": "결제 API 500 에러 발생",
  "description": "14시부터 결제 API에서 간헐적 500 에러 발생. 약 10%의 요청이 실패 중.",
  "service": "payment",
  "error_log": "java.lang.NullPointerException at PaymentService.process(PaymentService.java:142)"
}
```

**출력**:
```json
{
  "category": "앱",
  "severity": "Major",
  "keywords": ["결제", "API", "500에러", "NullPointerException"],
  "confidence": 0.92,
  "reasoning": "결제 서비스의 애플리케이션 레벨 에러로, NullPointerException이 발생. 간헐적이나 10% 실패율로 Major 판단."
}
```

### 구현 방식

- **LLM**: OpenAI GPT-5.1 (structured output / function calling)
- **프롬프트 전략**: Few-shot 예시 기반 분류
- **카테고리**: 인프라 / 앱 / DB / 네트워크 / 외부연동 / 기타
- **심각도**: Critical / Major / Minor

### 프로젝트 구조

```
손재명/week_3/
├── 핵심_에이전트_구현.md
└── src/
    ├── classifier/
    │   ├── agent.py          # 장애 분류 에이전트 메인 로직
    │   ├── prompts.py        # 프롬프트 템플릿
    │   └── schemas.py        # 입출력 Pydantic 모델
    ├── rag/
    │   ├── agent.py          # 유사 장애 검색 에이전트 메인 로직
    │   ├── embeddings.py     # 임베딩 생성 및 저장
    │   ├── retriever.py      # 벡터 유사도 검색
    │   └── schemas.py        # 입출력 Pydantic 모델
    ├── config.py             # 환경 설정
    ├── main.py               # 실행 엔트리포인트
    └── requirements.txt
```

## 2. 유사 장애 검색 에이전트 구현

### 기능 정의

- 분류된 장애 정보를 기반으로 과거 장애 이력에서 유사 사례를 검색
- 유사 사례의 해결 방법을 참고하여 1차 조치 가이드 제공

### 입출력 스펙

**입력**:
```json
{
  "category": "앱",
  "severity": "Major",
  "keywords": ["결제", "API", "500에러", "NullPointerException"],
  "description": "결제 API에서 간헐적 500 에러 발생"
}
```

**출력**:
```json
{
  "similar_incidents": [
    {
      "id": "INC-2024-0142",
      "title": "결제 API 타임아웃 장애",
      "similarity": 0.87,
      "resolution": "커넥션 풀 사이즈 증가 및 null 체크 추가",
      "resolved_at": "2024-11-15"
    }
  ],
  "suggested_actions": [
    "PaymentService.process() 라인 142의 null 체크 확인",
    "결제 API 커넥션 풀 상태 점검",
    "최근 배포 변경 사항 확인"
  ]
}
```

### 구현 방식

- **벡터 DB**: PostgreSQL + pgvector (로컬 개발 시 ChromaDB로 대체 가능)
- **임베딩**: OpenAI text-embedding-3-small
- **검색**: 코사인 유사도 기반 Top-5 반환
- **샘플 데이터**: 테스트용 장애 이력 10~20건 수동 생성

## 3. 기본 동작 검증 계획

### 검증 시나리오

| # | 시나리오 | 검증 항목 |
| --- | --- | --- |
| 1 | 명확한 인프라 장애 입력 | 카테고리 "인프라"로 정확히 분류되는지 |
| 2 | 애플리케이션 에러 로그 포함 입력 | 에러 로그 기반 키워드 추출 및 분류 |
| 3 | 모호한 장애 설명 입력 | confidence 값이 낮게 나오는지 |
| 4 | 과거 유사 장애 존재 시 검색 | 유사도 높은 사례가 Top-K에 포함되는지 |
| 5 | 과거 이력 없는 신규 유형 | 빈 결과 또는 낮은 유사도로 적절히 반환되는지 |

### 검증 방법

1. **단위 테스트**: 각 에이전트별 입출력 검증
2. **통합 테스트**: 장애 분류 → 유사 장애 검색 파이프라인 연결 검증
3. **수동 테스트**: 실제 장애 사례 기반 결과 품질 확인
